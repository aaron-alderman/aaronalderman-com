# Publication source boundary

The owner's controlling instruction is: zero JSON files. Static content enters
as REL. When scripting is required, Encounter must hydrate into REL before
admission. This applies to the website application and its publication path.

Do not create JSON files, executable preparation scripts, native content
generators, or a second authoring/admission path. Do not hide a JSON object or
programme inside a REL string, rename a JSON programme to REL, or treat generated
output as an authoring input. The retained kernel/mechanisms do not author
application policy, transformations, or publication composition.

The owner authorized publication and preservation of newer live changes on
2026-11-08. `bootstrap/publication.rel` remains the canonical source declaration;
`bootstrap/local.cjs` is its generic host. The host requires literal zero JSON
files before and after execution. Migration intake is retired. GitHub Pages
may publish only a fresh canonical build after the Encounter verification gate.
Do not restore the legacy build or deploy an archived `dist/`.

`verification/source-authority-audit.rel` records findings and unresolved work.
It is an audit, not an admitted executable policy or proof of compliance.
The former JSON sources, dependency cache, native helpers and migration intake
are archived intact outside this worktree under the local Codex visualizations
directory's `mission-compiler-retirement` folder. That archive is forensic
evidence, never a publication input or fallback. Historical source quotations
and browser receipts retain their original scope and date.

Before publication can resume, the actual selected source closure must satisfy
this boundary, and admission must reject alternative entry paths. Merely
changing suffixes, deleting evidence, or adding an extension check is inadequate.

Fact indexing, composition and sealing are explicit bounded phases. Each keeps
the 20,000,000-step limit. Nested calls and children share their caller's budget.
`host.admissionPlan` partitions the declared phases into bounded admission
cohorts. Each cohort receives its own real admission and fact-index handle;
serialized collections are evidence only and grant no execution authority.
Only opaque compiler-owned hydration, admission and fact-index handles confer
execution authority; serialized receipts and inspection models do not.

Application transformations, compiler/lowering logic, admission and sandbox
policy, source-inspection projections and host/markup permissions belong in
Encounter. `bootstrap/foundation.rel` pins that source. The operative laws and
schemas are produced by Encounter and hydrated into REL; retained REL tables
are display/application data and must not become policy bootstrap inputs.
Native code is limited to primitive execution, typed REL, hashing, capability
identity/transport, inert parsing, mechanical ports and fixed runtime packaging.
The bootstrap-only syntax reader is explicit trust: Encounter must re-parse its
pinned inputs, hydrate real REL, link and admit the operative policy image.
Normal application and dynamic child source must never use that native reader.
The 97 separated historical model/authoring records are static data under
`evidence/`; `bootstrap/publication.rel` maps their preserved logical publication
names to those physical files. Do not restore copies beside current programme
sources or select evidence files as executable modules. Current derived laws
belong in `source/foundation/laws.encounter`, with their foundation pin updated.
Start publication through `bootstrap/launch.cjs` so the exact bytes passed to
Node's compiler are captured; a later disk scan alone cannot attest loaded code.
Read-only verification code and the local static preview server are separate
from the publication's execution authority.

# Test source boundary

All test scenarios, fixtures with behaviour, assertions and audit pass/fail
decisions are authored in Encounter under `verification/tests/`. Run them with
`node bootstrap/test.cjs`; optional arguments select process-name substrings.
Bootstrap supplies discovery, reporting and mechanical adapters only. Do not
move JavaScript tests into bootstrap, rename them, wrap their execution in an
Encounter programme, encode them as strings, or retain a native assertion path.
Historical negative findings remain evidence, with their original scope.

There must be literally zero `.mjs` files outside the root `bootstrap/`
directory, including ignored/generated paths. The preview entry point is
`node bootstrap/serve.mjs`. The Encounter boundary test inventories the whole
worktree and rejects native test files and disguised executable suffixes.
